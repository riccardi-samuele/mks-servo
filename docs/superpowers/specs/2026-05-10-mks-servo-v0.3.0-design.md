# mks-servo v0.3.0 — Design Specification

**Status:** Approved (autonomous execution).

## 1. Goal

Add Level-2 namespaced advanced features (`motor.advanced`, `motor.diagnostics`),
a programmatic `CharacterizationSuite` to populate
`profile.characterization` from empirical tests, a `mks-servo characterize`
CLI command, and a driver model registry to make future SERVO57D support
mechanical.

End-user code:

```python
# Programmatic characterization
from mks_servo import Motor, CharacterizationSuite

with Motor.from_profile("wrist") as m:
    suite = CharacterizationSuite(m)
    results = suite.run_mvp()        # P1 + P3 + P5 + S2
    suite.update_profile()           # writes characterization back
    m.profile.save()

# Level 2: advanced and diagnostics namespaces
m.advanced.set_baud(115200)
m.advanced.set_slave_addr(7)
m.advanced.save_speed_mode_state()

print(m.diagnostics.protection_latched())
m.diagnostics.release_protection()
```

CLI:
```bash
mks-servo characterize wrist --suite=mvp
mks-servo characterize wrist --suite=full --update-profile
```

## 2. Out of scope (v0.3.0)

- `motor.homing.*` namespace — firmware homing flow needs hardware exploration
  first, deferred to v0.4.
- `motor.io.*` namespace — pin-level I/O, deferred to v0.4 (no urgent use case).
- Sphinx + readthedocs — over-engineering for pre-v1.0; markdown docs are
  enough until the open-source release.
- Real SERVO57D driver implementation — only the registry hook lands here,
  so a future contributor can drop in `Servo57DRaw` without touching `Motor`.
- Velocity mode on `Motor` — still rinviato to v0.4 (or never; benchmarks use
  `motor.raw.move_speed` directly which is fine).
- C1/C2/C3 persistence tests in the suite — they need a power-cycle, which
  is fundamentally manual. Skip from auto-suite.
- S1/S3 (mode-cap RPM tests) — known firmware bug; benchmarks document it,
  not worth re-running automatically.

## 3. Architecture

### 3.1 New: Level 2 namespaces

`Motor` gains two new attributes that lazy-construct namespace objects:

```
Motor
├── (Level 0)  attach, detach, write, read, error, is_moving, emergency_stop
├── (Level 1)  work_current_ma, microsteps, mode, direction, hold_current_pct,
│              position_limits, speed_limit_rpm,
│              set_origin, move_relative, enable, disable, wait_until_idle,
│              calibrate, restart, restore_defaults
├── (Level 2)  advanced.*           ← NEW
│              diagnostics.*        ← NEW
└── (Level 3)  raw                   (already public in v0.2.0)
```

Each namespace is a thin wrapper class that holds a back-reference to the
Motor and exposes a curated set of methods. Namespaces:

- `motor.advanced` — settings that change driver flash/state and are NOT
  needed for normal moves: `set_baud`, `set_slave_addr`, `set_respond_active`,
  `save_speed_mode_state`. (`restore_defaults` stays at Level 1 because it's
  the canonical "reset" operation that users find quickly.)
- `motor.diagnostics` — read-only health/status that's NOT covered by the
  Level-1 read-only properties: `protection_latched()`, `release_protection()`,
  `read_pulses_received()`, `query_status_text()`.

The namespace classes live in `mks_servo/namespaces.py`.

### 3.2 New: `CharacterizationSuite`

```
mks_servo/characterize.py
├── class CharacterizationSuite
│   ├── __init__(motor: Motor, *, output_dir: Path | None = None)
│   ├── run_p1_precision(iterations=5) → P1Result
│   ├── run_p3_error_vs_rpm(rpms=[50,100,300,500,1000]) → P3Result
│   ├── run_p5_follow_error(rpm=60, duration_s=2.0) → P5Result
│   ├── run_s2_acceleration(target_rpm=2000, accs=[1,50,100,255]) → S2Result
│   ├── run_mvp() → SuiteResult                # P1+P3+P5+S2
│   ├── run_full() → SuiteResult               # alias for run_mvp() in v0.3
│   └── update_profile() → None                # writes results into motor.profile
├── @dataclass class P1Result(...)
├── @dataclass class P3Result(...)
├── @dataclass class P5Result(...)
├── @dataclass class S2Result(...)
└── @dataclass class SuiteResult(p1, p3, p5, s2)
```

The suite reuses the analysis logic from `benchmarks/02_precision.py` and
`benchmarks/03_speed.py` but EXPOSES it as Python objects, not just CSV.

`update_profile()` writes the suite's findings back into
`motor.profile.characterization`:
- `precision.sigma_deg` ← P1Result.sigma_deg
- `precision.peak_deg` ← P1Result.peak_deg
- `speed.max_measured_rpm` ← S2Result.max_observed_rpm
- `speed.voltage_v` ← motor.profile (existing) — not mutated; user's job to fill
- `last_calibrated` is NOT touched (separately set by `motor.calibrate()`)

`update_profile()` does NOT save the YAML; caller invokes `motor.profile.save()`.

### 3.3 New: driver model registry

```python
# mks_servo/raw.py
DRIVER_REGISTRY: dict[str, type[RawDriver]] = {
    "servo42d": RawDriver,
    # "servo57d": Servo57DRaw,  # to be added when implemented
}


def make_raw_driver(model: str, **kwargs) -> RawDriver:
    """Factory: look up the driver class for `model` and instantiate it."""
    cls = DRIVER_REGISTRY.get(model)
    if cls is None:
        raise ProfileError(f"unknown driver model: {model!r}")
    return cls(**kwargs)
```

`Motor.from_profile` and `MotorBus.add` both go through `make_raw_driver(profile.driver.model, ...)` instead of constructing `RawDriver` directly. For now, the only entry is `"servo42d" → RawDriver`. Adding SERVO57D in a future PR is just registering the new class.

Backward compatibility: `RawDriver(addr=..., transport=...)` still works as before; the registry is layered on top, not replacing anything.

### 3.4 New CLI: `mks-servo characterize`

```bash
mks-servo characterize <profile> [--suite=mvp|full] [--update-profile] [--save]
```

Behaviour:
- Loads the profile.
- Opens a Motor with that profile (must have `transport.port` set, or pass `--port`).
- Runs the requested suite.
- Prints results.
- If `--update-profile`, writes characterization back into the profile (in-memory).
- If `--save`, also calls `profile.save()` (requires `--update-profile` to be useful).

## 5. API specifications

### 5.1 `motor.advanced`

```python
class AdvancedNamespace:
    """Driver-flash-modifying configuration NOT needed for everyday motion."""
    def __init__(self, motor): self._motor = motor

    def set_baud(self, baud: int) -> None:
        """Change the serial baud rate (cmd 0x8A). Persists in driver flash.
        Requires reconnecting at the new baud."""

    def set_slave_addr(self, addr: int) -> None:
        """Change the slave address (cmd 0x8B). Persists in flash.
        Profile.driver.slave_addr is updated to match."""

    def set_respond_active(self, active: bool) -> None:
        """Cmd 0x8C: enable/disable active response from the driver."""

    def save_speed_mode_state(self) -> None:
        """Cmd 0xFF: save the current speed-mode setting persistently."""
```

Each method goes through `self._motor.raw.<method>` and updates
`self._motor.profile` where appropriate (e.g., `set_slave_addr` mutates the
profile's `driver.slave_addr`).

### 5.2 `motor.diagnostics`

```python
class DiagnosticsNamespace:
    """Read-only diagnostics + protection-clear actions."""
    def __init__(self, motor): self._motor = motor

    def protection_latched(self) -> bool:
        """Cmd 0x3E: True if motor stall protection is currently latched."""

    def release_protection(self) -> None:
        """Cmd 0x3D: clear stall-protection latch."""

    def pulses_received(self) -> int:
        """Cmd 0x33: cumulative pulses received since power-on."""

    def status_text(self) -> str:
        """Human-readable status: `'STOPPED'`, `'CALIBRATING'`, etc."""
```

### 5.3 `Motor` lazy attributes

Inside `Motor`:

```python
@property
def advanced(self) -> "AdvancedNamespace":
    if self._advanced_ns is None:
        from mks_servo.namespaces import AdvancedNamespace
        self._advanced_ns = AdvancedNamespace(self)
    return self._advanced_ns

@property
def diagnostics(self) -> "DiagnosticsNamespace":
    if self._diagnostics_ns is None:
        from mks_servo.namespaces import DiagnosticsNamespace
        self._diagnostics_ns = DiagnosticsNamespace(self)
    return self._diagnostics_ns
```

Lazy construction: zero overhead for users who don't touch these namespaces.

### 5.4 `CharacterizationSuite` results

```python
@dataclass
class P1Result:
    """Repeatability — same target N times, measure the read-back spread."""
    target_deg: float
    iterations: int
    samples_deg: list[float]
    mean_deg: float
    sigma_deg: float
    peak_deg: float        # max |sample - target|


@dataclass
class P3Result:
    """Error vs commanded RPM."""
    rpm_samples: list[int]
    rms_error_deg: list[float]   # one per rpm sample


@dataclass
class P5Result:
    """Follow error during a sweep at constant RPM."""
    rpm: int
    duration_s: float
    max_follow_err_deg: float
    rms_follow_err_deg: float


@dataclass
class S2Result:
    """Acceleration curves to a target RPM with varying acc parameter."""
    target_rpm: int
    accs: list[int]
    time_to_target_ms: list[float | None]   # None if didn't reach target
    max_observed_rpm: int


@dataclass
class SuiteResult:
    p1: P1Result | None = None
    p3: P3Result | None = None
    p5: P5Result | None = None
    s2: S2Result | None = None
```

### 5.5 `CharacterizationSuite.run_*` methods

Each `run_<test>(...)` method:
1. Returns its result dataclass.
2. Stores it in `self._last_results`.

`run_mvp()` runs `run_p1_precision`, `run_p3_error_vs_rpm`, `run_p5_follow_error`,
`run_s2_acceleration` in sequence and returns a `SuiteResult`.

`update_profile()`:
- Reads from `self._last_results`.
- Updates `motor.profile.characterization.precision.sigma_deg/peak_deg` from P1.
- Updates `motor.profile.characterization.speed.max_measured_rpm` from S2.
- Does NOT save.

## 6. Testing strategy

### 6.1 Unit tests (mocked motor — no hardware)

- `tests/test_motor_namespaces.py` — namespaces exist as lazy properties; calls
  through to `motor.raw.*` correctly.
- `tests/test_characterize_suite.py` — fake motor with deterministic `read()`
  values; verify:
  - `run_p1_precision` returns a P1Result with correct sigma/peak.
  - `run_p3_error_vs_rpm` runs all RPM samples.
  - `run_p5_follow_error` returns a P5Result.
  - `run_s2_acceleration` returns an S2Result.
  - `run_mvp` returns a SuiteResult with all four populated.
  - `update_profile` writes p1/s2 fields into profile.characterization.
- `tests/test_cli_characterize.py` — CliRunner with patched
  `Motor.from_profile` / `CharacterizationSuite`; verify exit codes and that
  `--update-profile` + `--save` propagate.
- `tests/test_raw_registry.py` — `make_raw_driver("servo42d")` returns a
  RawDriver; unknown model raises `ProfileError`.

### 6.2 HIL tests

None new in v0.3.0. The CLI `mks-servo characterize` IS the manual HIL
exercise; no automated HIL test is written for it (it's the user's
characterization workflow).

## 8. Acceptance criteria

v0.3.0 is "done" when ALL of:

1. `motor.advanced.set_baud(115200)` calls `motor.raw.set_baud(...)` (or the
   underlying opcode).
2. `motor.diagnostics.protection_latched()` returns a bool.
3. `from mks_servo import CharacterizationSuite` works.
4. `suite = CharacterizationSuite(motor); res = suite.run_mvp()` returns a
   `SuiteResult` with all four fields populated (mocked test passes).
5. `suite.update_profile()` writes the precision sigma/peak and max RPM into
   the profile (mocked test passes).
6. `mks-servo characterize <profile> --suite=mvp` works against a mocked motor.
7. `make_raw_driver("servo42d", ...)` returns a `RawDriver`. Unknown model
   raises `ProfileError`.
8. All v0.2.0 tests still pass.
9. CHANGELOG and README updated.
10. `examples/characterize_motor.py` parses cleanly.

## 9. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Namespaces clutter `Motor` autocomplete | Use property lazy-loading; properties show as ordinary attributes, no name pollution |
| CharacterizationSuite duplicates benchmark logic | Keep benchmarks/ for CSV/PNG output; suite returns dataclasses for programmatic use. Cross-pollinate logic where simple. |
| New CLI command discovered late by users | Document in README, multi-motor.md, characterization.md |
| Servo57D registry could grow | Keep the registry minimal — just `dict[str, type]`; if it gets complex, a real plugin discovery pass goes in v0.4 |
